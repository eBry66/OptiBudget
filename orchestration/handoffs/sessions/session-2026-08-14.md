### 3. Process lessons

- Verify content via git diff or Select-String -Context, not tool
  summaries or Get-Content -Raw console output.
- PowerShell here-strings with a blank interior line are not reliable for
  appends - build the join explicitly in code instead.
- git add . bundles whatever's sitting on disk, ready or not - check git
  status first.
- DOC-id documents need next.mjs approve; non-DOC-id content does not,
  but a DECISIONS.md entry about non-DOC-id content still requires
  approving DECISIONS.md itself.
- A "no violations found" review with no specifics is not sufficient
  evidence - push for what was actually checked.
- A failed variable assignment in PowerShell leaves the variable at its
  PRIOR value rather than empty - a script that continues after an error
  can silently use stale data from an earlier command. Always check
  command success before using a variable downstream, especially across
  multi-step scripts reusing variable names.
- Cross-session file handoff via download/upload is unreliable in this
  environment - three attempts this session failed on the file never
  actually landing on disk, none being a content problem. Prefer
  self-contained PowerShell here-strings over external files when
  content needs to move from chat into a repository file.

### 1. Branch-first habit, adopted but not yet formalized

`git push` on `main` failed every time it was attempted this session -
branch protection makes this a guaranteed rejection, not a real check.
Going forward: skip the direct push attempt entirely, branch immediately.

```powershell
git checkout -b fix-<description>
git push -u origin fix-<description>
```

Not yet written into HITL_GUIDE.md as a formal procedure change - worth
doing next session, since it's a genuine, repeatable time cost.

### 2. Open question, deliberately not decided: does every HITL document
edit need the full PR cycle?

Branch protection's original rationale (HITL_GUIDE.md section 8.1) targets
agent-implemented task work - forcing review before code merges. Most of
what went through the PR cycle this session was HITL-authored document
edits, drafted in chat, with no agent involved and no real review
happening (per section 17.3, the HITL cannot approve their own PR, so the
"review" step is rereading the same diff a second time on GitHub instead
of the terminal). A real case exists for treating agent task work and
pure HITL document edits differently under branch protection. Not
resolved - flagged for deliberate review next session, not a same-session
decision.

### 3. Real lesson: a merge was assumed successful without verification,
caught late

During this session's closing stretch, a PR merge was inferred from
adjacent command output (branch push succeeding, cleanup commands
running without error) rather than confirmed directly. `next.mjs check`
only validates local repo state - it has no way to know whether
`origin/main` actually received the merge. The gap was only caught by
explicitly running `git log origin/main --oneline` and comparing against
the expected commit hash. Standing rule going forward: after any PR
merge, confirm with either GitHub's literal "Pull request successfully
merged and closed" message, or `git log origin/main --oneline -3`
showing the expected commit as the new top of `origin/main` - never infer
a merge succeeded from surrounding command output alone.
